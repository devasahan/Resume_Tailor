# Resume Tailor

A resume tailoring app that works differently from the usual one.

- Your **base resume holds only fixed facts**: name, contact details, employers (with dates and remote/onsite) and education. Code locks these. The AI never writes or changes them.
- The AI **writes everything else from the job description**: headline, summary, skills, a job title per employer (the titles form a believable career path that climbs into the target role's field, for example Junior Software Engineer, Software Engineer, Platform Engineer, AI Platform Engineer, then Senior AI Platform Engineer for a "Senior AI Platform Engineer" post, and the headline under your name and the summary's first words repeat your most recent title), and the bullets under each employer, built around that company's main product during your dates there (for example a marketplace, a learning platform or an AI assistant) when the model knows the company.
- The result is a **single-column, ATS-friendly one-page resume** (about 450 words; two pages only for a career too long for one even with one bullet per older job; PDF and DOCX), plus an optional matching cover letter in plain words: one page under the same header as the resume (name, headline, contact line), starting right at the greeting ("Dear Hiring Manager,") and ending with a typed signature.
- **Before you tailor, see the basics of the job**: right after you paste a job post, the AI shows under the box whether it is remote, hybrid or on-site (with details such as the office days) and the salary it states, or "Not stated". It takes a few seconds and a tiny cost, and the same post pasted again costs nothing.
- It is **multi-model**: pick any model per run, tick several to compare them side by side, set defaults and fallbacks, and change models at any time without touching code.

> Everything the AI writes is a draft. It cannot know your real history, so the app flags every number and every inferred skill for you to confirm. Do not send a resume you have not read.

## Run it on your PC

You need **Python 3.11 or newer** and nothing else: no API key, no other software. The app runs in **demo mode** (three offline demo models) until you add keys, so you can try the whole flow first.

| Your computer | Do this |
|---|---|
| **Windows** | 1. Install Python from <https://www.python.org/downloads/> and tick **"Add python.exe to PATH"** (or run `winget install -e --id Python.Python.3.12`).<br>2. Get the project (green **Code** button > **Download ZIP**, then unzip, or `git clone`).<br>3. Double-click **`start.bat`**. |
| **macOS / Linux** | 1. Python 3.11+ (macOS: <https://www.python.org/downloads/> or `brew install python`; Ubuntu/Debian: `sudo apt install python3 python3-venv`).<br>2. In the project folder run **`./start.sh`**. |
| **By hand** | `python -m venv .venv`, activate it (`source .venv/bin/activate` or `.venv\Scripts\activate`), `pip install -r requirements.txt`, `python -m app` |

The first start takes a minute or two (it creates a private `.venv` folder and installs the libraries). Your browser then opens at <http://127.0.0.1:8000>. Press **Ctrl+C** (or close the window) to stop it.

**Log in first.** The app has accounts. Open `.env` (`notepad .env` on Windows), add your own `ADMIN_EMAIL=` and `ADMIN_PASSWORD=` lines, save, and start the app again; then log in with them. That is the admin account. See [Accounts](#accounts).

If something does not start, run **`python -m app.doctor`**. It checks Python, the libraries, PDF and DOCX export, the data folder, API keys and the port, and says how to fix each problem.

### Try the demo (about two minutes)
1. **Profile** > drop `evals/sample_base_resume.docx` (or `.pdf` / `.txt`) on the page, or **Choose files**. It is read and saved at once and appears in the list.
2. **Tailor** > pick the base resume > paste a job description (for example `evals/jds/01_data_engineer.txt`) > paste its link into **Job link** (the sample posts have none: any `https://` address works for a try, for example `https://jobs.example.com/data-engineer`) > **Create resume & cover letter**.
3. **Download resume PDF** and **Download cover letter PDF**. (**Resume only** skips the letter; **Add cover letter** writes it later for the same resume, and **Rewrite cover letter** writes a new one.)
   Files are named the usual way for applications, name then document: `Jordan_Rivera_Resume.pdf` and `Jordan_Rivera_Cover_Letter.pdf` (a name in capitals gets normal capitals).

The demo models write generic template text. They exist to show the flow (fit to one page, flags for invented numbers, retries); they say nothing about what real models write.

### Then add real models
1. Copy `.env.example` to `.env` (the start script does this for you) and open `.env` in any text editor.
2. Paste the API key for the provider you have, for example `ANTHROPIC_API_KEY=...`. Or log in as the admin and paste it on **Settings > API keys**: it is saved in `.env` for you. Use **paid** keys: free tiers may let the provider train on your data.
3. A new or changed key works at once, with no restart. In **Settings**, press **Run check** to confirm each key and model name works (one tiny call per model, a fraction of a cent).
4. In **Settings**, choose the **Resume model** and **Cover letter model** the Tailor page uses (Automatic picks the first available, Gemini 3.8 Flash first when `GEMINI_API_KEY` is set). Costs are shown per run. To compare models side by side, use the bake-off below.

Nothing leaves your computer except the calls to the model providers you pick. See [Privacy and security](#privacy-and-security).

## Accounts
- **Admin**: the one account whose email and password are in `.env` (`ADMIN_EMAIL`, `ADMIN_PASSWORD`). It has every page: Profile, Tailor, **History**, **Users** and **Settings**. The password is never stored in the code or the database (only a one-way hash). To change it, edit `ADMIN_PASSWORD` and restart: the new one replaces the old one and ends every admin session.
- **Users** sign up on the **Sign up** page. A new account waits until the admin approves it on **Users** (Approve or Reject). A user sees only **Profile** (upload resumes) and **Tailor** (tailor, make a cover letter, download both PDFs): no History, Users or Settings, no model names or costs. Each account sees only its own resumes and results.
- **Users page**: approve or reject sign-ups, disable or enable an account, give a user a one-time temporary password (they change it on their **Account** page), or delete an account with its resumes and runs.
- **History** lists every click on a **Download** button, by every account (users and admin), with the account, the resume, company, job title, the job post's link (**Job link**: the site's name, opening the post in a new tab; only `http://` and `https://` addresses are links, and rows from before it was kept show "-"), model and cost. Filter it by account (active accounts only; rows of disabled or removed accounts are tagged) and by typing part of a company or job title, in any case. Each row opens the job's resume, its cover letter (when it has one) and the job description in a new tab (its first lines name the company, the job title and the job link); these previews are not counted. A row keeps its job link after its run is deleted. History is deleted after the retention period.
- After 5 wrong passwords an account is locked for 15 minutes (restarting the app clears the admin's lock). The daily cost cap is shared by everyone: one busy user can reach it for the whole site.

## Using it
1. **Profile**: upload one or more base resumes (PDF, DOCX, TXT). Each is read and saved right away and listed with its employers, education, certifications and anything to double-check (for example "Phone not found"). The reader is set in Settings > Base-resume reader: Automatic uses the cheapest available model (the resume text is sent to that provider), **Rules only** reads it on your machine for free. If a read is wrong, delete it and upload again. Uploaded resumes stay until you delete them. Each one also has **Projects you worked on**: under each employer, list the products and projects you really worked on there (one per line, with dates if you know them; up to 4,000 characters each; notes pasted from research can stay as they are: links and lists of sources are left out of what the AI reads) and press **Save projects**. Tailoring then writes that employer's bullets about this work, as yours: it names the products and projects and describes your part in them in the job post's terms (what you built or ran for it, how, and what changed). A project dated outside the job's dates is left out of it, figures are used only as you wrote them, and the notes themselves are never printed. When you upload the same person's resume again (the same name), each employer keeps the notes of your newest earlier upload that lists it, and the card says so; notes you cleared stay cleared. Each one also has **Certifications you have passed**: paste the certifications this person passed, one per line as `name | issuer | date earned - date it expires` (for example `AWS Certified Developer – Associate | Amazon Web Services | Mar 2024 - Mar 2027`; rows copied from a table work too, with Issued and Expires columns; the number and exam-code columns are left out), and press **Save certifications**. LinkedIn's "Issued ... · Expires ..." lines in an uploaded resume are read the same way. While **Settings > Certifications section** is on, the best ones that fit each job, up to 4, are then printed automatically, with nothing to tick. It is off by default: then nothing is printed, and the list stays saved here for later. List only exams that were really passed: employers check them.
2. **Tailor**: pick a base resume, paste the job description (the company's name, the work mode and the salary are then read from it and shown under it; the **Company** box is filled with the name exactly as the post writes it, and when the post names no company you copy its name into the box before tailoring: the cover letter and History use it; paste the job post's address into the **Job link** box: copy it from the browser's address bar on the post's page, and `https://` is added when it is missing. Both boxes are marked **required**: no button starts without them, and pasting another job post empties a link entered for the one before. The link is kept with the run for History and is never sent to the AI. After the browser's Back button, paste the link again), choose **US style** (the default: American spelling) or **EU style** (British spelling as used in the UK and the EU: optimisation, behaviour, centre; the letter signs off "Kind regards," and calls the resume a CV, and the download is "Download CV PDF", named "Your_Name_CV.pdf"). Names keep their own spelling (Unity Catalog, your employers), and so do the job post's own keywords, because an ATS matches them letter for letter; if the post is written in the other spelling, the Format notes say so. Then press **Create resume & cover letter**. One step, "Writing your resume and cover letter", shows the time so far: the resume and its letter are made in one go, and the letter is written from the final resume text while the app lays out the pages, so it adds little to the wait (usually about 30 seconds in all with Gemini 3.8 Flash). The resume model comes from Settings. If the letter could not be written (the AI service was busy, or the daily cost cap was reached), the resume is still ready and the page says so: press **Add cover letter** to try again.
3. The cover letter is one more call, added to the same run's cost. **Resume only** skips it; **Add cover letter** writes it later for that resume, and **Rewrite cover letter** writes a new one without tailoring the resume again (a corrected **Job link** is recorded with it; the resume stays as it is). For the admin, a line under the result shows where the time went, for example "AI 21.4 s (8,214 in / 1,912 out + 2,105 thinking) · cover letter 6.1 s, alongside · layout and checks 1.3 s · total 27.7 s (this page 28.3 s)": the AI's time for the resume and its tokens (thinking counted apart), the letter's own time ("alongside" when it was written during the layout, so the wait was shorter), the app's own work, and the whole job (and what the page waited, network included). It is not shown after Add or Rewrite cover letter. Every run keeps this record, with each AI call's model, time, tokens and result.
4. **Certifications for this job** (only while **Settings > Certifications section** is on; with it off, the default, the page shows no certifications and the resume has no Certifications section): under the downloads, the AI lists the 4 best, highest-level certifications for this job, each with an **I have it** tick box. Only ticked ones are printed on the resume, in a CERTIFICATIONS section after EDUCATION, with their dates on the right ("Mar 2023 - Mar 2026": earned - expires; only the date earned when it does not expire), and the preview and downloads change at once. A certification whose expiry date has passed is never picked or printed; the Profile page lists it as expired, so you can change the date when it is renewed. The ones your uploaded resume lists (or you pasted on the Profile page) start ticked, and every tick (or untick) is remembered on that base resume for your next jobs. When you have 4 or more that fit the job, all 4 are your own. The others are ideas to earn; they are never printed unless you tick them.
5. **Download resume PDF** / **Download cover letter PDF**. There is no manual editing step: the app checks and fixes the draft itself (one page, one title under your name, in the summary and at your current job, title path, the post's programming language at your current job, required skills, thin text, figures) before you see it. History keeps the PDFs of every run.

## Models

`models.yaml` is the registry. A model is usable when its API-key variable is set (see `.env.example`, or paste the key on Settings > API keys) and its data region is allowed in Settings.

| Provider type | Used for | How |
|---|---|---|
| `anthropic` | Claude Sonnet 5.5 | Official Anthropic SDK; JSON schema via `output_config.format`, adaptive thinking, refusal fallback |
| `openai_compat` | Gemini, GPT (OpenAI), Grok, Mistral, DeepSeek, Qwen, GLM, Kimi | One adapter for any `POST {base_url}/chat/completions` API. If a provider rejects `json_schema` or `reasoning_effort`, it retries with fewer features and remembers what worked |
| `fake` | Offline demo models | No network, no cost |

**To add a model**, add an entry to `models.yaml` (id, model string, base URL, key variable, price, region), set the key, restart. No code change is needed for any OpenAI-compatible provider.

**Gemini 3.8 Flash (fast)** is the same model with the least thinking ("minimal"), for faster drafts, so the polishing pass fits the time limit more often. It is marked unverified: tick it under Check models in Settings and press Run check. If Gemini refuses the setting, the check fails (the app never quietly falls back to slower thinking); if it passes, choose it as the Resume model and compare the "job finished" lines in the server log (each AI call's line also shows its thinking tokens).

**GPT** needs an OpenAI API key (`OPENAI_API_KEY`) from platform.openai.com, paid per use: a ChatGPT Plus or Pro subscription cannot be used by apps. Its model name and price are marked unverified until the check on the Settings page passes.

**Models marked `verified: false` need checking.** Their model strings and prices came from third-party websites in October 2026 and were not confirmed against the vendors. Run:

```bash
python -m app.cli models          # what is available
python -m app.cli check           # one tiny real call per model (cents): verifies key, model name, JSON mode
```

Costs shown in the app are estimates: `tokens reported by the provider x the price in models.yaml`. Reasoning tokens usually count as output tokens.

### Settings (applied to new runs immediately)
- default model for the resume, the cover letter and for reading the base resume
- fallback models, tried in order when the chosen one fails (not used in Compare, where each result must show one model alone). A slow answer is waited for, never cut short to save time: the chosen model gets 2 minutes before the next one is tried, and the last model about 4 minutes (the connection's own limit), so a slow AI day means a longer wait, not a failed resume. A **busy** answer is different (Google's HTTP 503 "This model is currently experiencing high demand", another server error, Anthropic's "overloaded", or a plain "too many requests" once the connection's own retries are used up, which wait a few seconds or as long as the provider asks): the next model is asked at once, and when no model answered, the busy ones take turns, the chosen model first, after short pauses (2, 5, 10, 15, 20 and 25 seconds), until one answers; a busy rewrite pass is asked again the same way while its time allows. After about a minute and a half of busy answers and pauses the run stops: when every model was still busy it says plainly which company is busy (after "too many requests": overloaded, or the key's rate limit was reached), else it lists each model's last error (the base-resume reader stops after about 45 seconds and uses the built-in rules). **Run check** asks a busy model once more after 3 seconds. With a backup from **another company** (for example Claude Sonnet 5.5), a Google overload costs only a few seconds: Settings warns when every backup uses the resume model's key. A cover letter written with the resume is waited for up to 2 minutes; after that the resume comes without it, with the note to press Add cover letter. A model that was slow, busy or unreachable is asked first again in the next run, so most resumes come from the chosen model. When a key's **quota is used up** (Google: "You exceeded your current quota, please check your plan and billing details"), the app says so at once, does not retry, and rests that model for an hour, or less when the provider says when the quota resets (reload the web app to try it again sooner): check the plan and billing at aistudio.google.com (free-tier keys have low daily limits; paid keys also keep your data out of training), and pick a backup that uses **another provider's key** (for example GPT-6.1 Sol), because backups that share the key stop too: Settings warns when they do. Every failed attempt is in the server log with its reason.
- a **soft daily cost cap** (new runs stop once today's recorded spend reaches it; runs already in flight finish; the day starts at midnight in Arlington, Texas)
- allowed data regions (models hosted in `CN` or `UNKNOWN` regions stay off until you allow them)
- retention (tailored runs are deleted after N days; uploaded resumes stay until you delete them), paper size (Letter / A4)
- numbers in bullets: realistic estimates flagged for you to confirm (default), or only the numbers you give
- **Certifications section** (off by default): when on, for each job the AI picks the best 4 of your certifications (the ones saved on the Profile page) and prints them after Education, and the Tailor page lists its picks with **I have it** ticks. When off, no Certifications section is printed, the Tailor page shows no certifications, and the AI is not shown your certifications: it only lists the ones the job post names, which are never printed (a slightly shorter prompt); certification names still stay out of the skills and the text. The lists saved on the Profile page are never changed by the switch: they stay for later. Resumes made before a change keep their own section (or lack of one).
- **time limit for a resume and its cover letter** (default 30 seconds): the first draft always comes back; the extra rewrite pass runs only when it can finish within the limit (a rewrite is expected to take at least half as long as the draft, or as long as the last one took), and is stopped at the limit, keeping the first draft with the app's own fixes (one page, titles, tense, numbers, names, dashes, spelling). With a cover letter, the time the last letter took with that model (8 seconds before the first one) is kept free as well, so the letter is ready with the resume; the trade-off is that the rewrite pass runs less often (with Gemini 3.8 Flash's 19-27 second drafts it rarely fits either way). A letter written with the resume is waited for up to 2 minutes in all (a backup letter model gets its turn after 1 minute); Add cover letter and Rewrite cover letter wait for the letter's model as long as a resume does (see fallback models). A rewrite that removes a certification named in the text always runs. 0 = no limit: always polish, best quality but slower. Each job's time per step is in the server log ("job finished in ...").

## Choosing a model: the bake-off

Nobody can tell you which model writes your resumes best; measure it.

```bash
# put 10-20 real job descriptions in evals/jds/*.txt, your own facts in evals/my_profile.json
python -m app.cli bakeoff --jds evals/jds --profile evals/my_profile.json \
    --models claude-sonnet-5-5,gemini-3.8-flash,mistral-large --out out/bakeoff
```

It prints a cost estimate and asks before spending anything, then writes `results.csv`, `summary.md` and one PDF per job and model. Compare the PDFs blind. The summary reports the on-one-page rate, keyword match, how many unverified numbers each model invented, cost and speed. It does not score writing quality. The `/api/tailor` endpoint also takes `model` and `compare` for scripted comparisons, and `company_name` and `job_link`, both optional there (a link must be an `http://` or `https://` address of up to 2,000 characters, or the request gets 422).

## How the guarantees work
- **Fixed facts cannot change.** The model returns only the editable sections as JSON. Code merges them into your saved profile and asserts the profile is unchanged. The edit endpoint never reads profile fields from the request.
- **Years of experience are calculated, not guessed.** The app computes them from your locked employment dates (overlapping jobs counted once, rounded down, e.g. "7+ years") and gives that figure to the model, which must use it exactly in the summary.
- **Metrics are estimates until you confirm them.** By default (Settings > Numbers in bullets) the model adds realistic, specific-looking metrics where they count: each job's first bullet gives its size and its result, the current job puts a figure in up to 2 more bullets and every other job in at most 1 more (at most 3 bullets with figures in the current job and 2 in every other job; older or short roles usually only the first), using real numbers passed as `hints` (API and CLI only) first. A figure you gave stays yours however the resume writes it (your "40 percent" is its "40%", your "5 million dollars" its "$5M"), and only as a whole: your "$12 million" never makes an invented "2M" yours. Under "No figures" your own figures never count against that limit. A percentage never stands alone: about half of the results give only the real numbers ("cut pipeline runtime from 47 to 36 minutes", "saving $41,000 a year in cloud spend"), and every other percentage comes with its base in words ("by 41.2%, from 97 to 57", "from 847 to 669ms, a 21% drop", "by 17.8%, or $41,000 a year"). No two figures are written the same way, and a base in brackets ("by 22% (from 41 to 32 seconds)") appears at most once in the resume and once in the letter: the app rewrites any later one itself, at no cost, as the real numbers alone or in words, taking turns (a percentage you gave is always kept, and a bracket that would read awkwardly either way is left as it is), and writes 62% rather than 62.0%. Text you edit yourself is never changed. The app checks that a before-and-after base agrees with its percentage (units included: 1.2s to 818ms is 31.8%). Money is written in the currency of the country where that job was. Switch the setting to "No figures" to forbid estimates.
- **Each job opens with its biggest win.** A recruiter scans a resume for about six seconds and reads only the first bullet of each job, so that bullet is the job's strongest achievement for the posting, with its size and its result ("for 83K concurrent players, cutting queue-to-lobby time from 41 to 32 seconds"; in words under "No figures"), never a general duty. If the most recent job, or two or more jobs, open without a figure, the same single rewrite pass moves one up, and the Format notes point out anything left.
- **A certification is printed only when you have it.** The model picks the certifications that fit the job, first your own (by their number in the list it is given) and then the most respected ones you do not have yet; code prints only your own, exactly as you wrote them, and checks that every printed one is in your saved list. A certification is never a "required skill", never in the Skills list and never named in the summary or bullets (the model is told so, certification skills are removed, and a name left in the text is sent back in the one rewrite pass), so unticking one really takes it off the resume. While **Settings > Certifications section** is off (the default), nothing is printed at all: the model only lists the certifications the job post names, and those checks still keep certification names out of the skills and the text. In both modes they also catch the well-known credential abbreviations a job post names (CISSP, CCNA and the like), whatever the model lists; an abbreviation that also means something else (PMP, CISM, CISA, CSM) counts only where the post names it as a credential ("PMP required", "PMP or PRINCE2"), so "PMP deals" in an ad-tech post stays.
- **Related skills are marked.** The skills list starts with the job description's skills, then adds closely related skills that support them (frameworks, libraries and services, not only platforms); each added one is flagged so you keep only what you really have.
- **One page, richest where it matters.** A reviewer's rule: fit one page by cutting words, never the font or the margins. Before the model writes anything, the app works out how many bullets each employer gets on one page at the design's own sizes (10.1 pt text, 0.67 in side margins), with every bullet two lines: the most recent job gets 2 and every other job 1, then the most recent job's extras until it holds about half of all the bullets (about half the page: it may take 6 once it has lasted 6 months, however short the older stays, and up to 8 after a long stay), then the older jobs' extras, to recent jobs and long stays first, and between jobs otherwise equal, to the one whose project notes share more with the posting; the most recent job always keeps the most. The plan fills the page: it may run over by less than one bullet, because real bullets are often shorter than two lines. With a contact line and stays of about 3 years, a 3-job career gets about 6 / 3 / 3 bullets, 5 jobs about 5 / 2 / 1 / 1 / 1 and 7 jobs 3 / 1 / 1 / 1 / 1 / 1 / 1. Only when even that minimum does not fit one page is the resume planned for two (a long career of many jobs, where the most recent job's extras also come first), and the model is told so. If a draft still runs over, the app removes bullets, never the first of a job: the most recent job's last bullet only while it holds more than half of them, else the last bullet of the older job with the most bullets, the job whose bullets show fewer of the posting's skills first, then the older one; the most recent job keeps the most bullets, and a bullet that holds a required skill's only mention goes last. A draft as long as its plan loses one bullet. With no time limit (Settings > Time limit 0, or Compare) and two or more bullets to remove, the model is first asked once for a draft with that many bullets. Only when two pages cannot be reached at the design's sizes is the font reduced (down to 8 pt), with a note. A job is never split across a page break: its title line and all its bullets stay on one page (PDF and Word), and a page break never falls inside a bullet or leaves a heading alone at the bottom. Resumes saved before keep their own layout, and their Format notes keep the length limits they were written to.
- **Strong bullets and summary.** Every bullet is one sentence of 15-22 words (two lines at most) that opens with a strong verb and says what was built, how (the 1-3 tools the work needed) and what changed, in plain words a person would use (no "leveraged", "spearheaded", "seamless" or chains of "-ing" clauses), and the bullets end in varied ways (at most one per job with a "so ..." clause). Bullets of the current job are in the present tense ("Build", "Lead") and those of every other job in the past ("Built", "Led"): an opening the model writes in the wrong tense is fixed by the app itself, at no cost (an opening that reads as a noun, such as "Shared dashboards replaced ...", is left alone), and a bullet it cannot change safely, such as one with a second verb in the same tense ("Rebuilt the sync service in Go and added retries"), is named for the rewrite pass and in the Format notes. A bullet never opens with a weak verb ("Used", "Supported", "Run", "Helped", "Responsible for") and never ends by saying who the work was done with (the app removes such an ending when the bullet still has at least 15 words and keeps every required skill). The summary is 2-3 sentences of 30-40 words (two or three lines): the experience, the current focus and one result, never self-praise ("Brings sound tradeoff judgment") or the skills list again; a praising sentence, or a 4th one, is removed by the app unless it holds a required skill's only mention. The current job's bullets carry its numbers (users or runs per day, tests and regressions caught, a cost saved): the AI uses your own numbers from the project notes first, and a note says when that job's notes have none. If a draft comes back thin, sounds machine-written, or breaks these rules in two or more places (weak openings, bullets in the wrong tense, 3-line bullets, a summary of 5 lines or more, praise, "so" endings; a 4-line summary or a single bullet in the wrong tense is named only along with other fixes), the model is asked once to rewrite it (when the time limit leaves room), and the Format notes point out anything still left.
- **Numbers, names and skills one way.** Every number is a numeral ("7 schools", "under 5 days"), and every figure is written the same way ("500K+", "$1.2M", "38%", "684ms"); a tool is written as its maker writes it (PostgreSQL, pytest, GitHub, Node.js), the same way everywhere, unless the posting uses another form, which then wins for the job sites' keyword scans. The AI names the real product (Google Calendar, HashiCorp Vault) where your notes do. Skills come in at most 3 rows, the posting's required skills first, and list only what the summary or a bullet shows (the posting's own keywords stay). Education prints the degree as on your diploma and the school's town ("B.S. in Computer Science · School · St. Louis, MO"): fix both in the Education box on the Profile page.
- **No signs of AI writing.** Following a recruiter's advice, the resume and cover letter avoid what reads as machine-written: no dashes used as punctuation (the model is told to use full stops and commas, and any dash it still writes becomes a comma; hyphenated words, ranges such as 2019-2021 and command-line flags stay), no vague results such as "improved operational efficiency" or "increased decision making", no percentage without its base, and no spelling that does not fit the market (see US style / EU style under **Using it**). Two or more vague results or bare percentages in a draft are rewritten in the one rewrite pass; a single one, and anything in the cover letter, is shown in the Format notes. Text changed through the editing API is kept as typed, with the same notes.
- **Every required skill is covered, in the posting's own words.** An ATS matches words, not meaning, so the model must show each must-have skill from the job description word for word ("schema design", not "schema changes") in the summary or a bullet, at the most plausible employer, without you supplying facts. A skill that is only listed under Skills does not count. If the first draft misses any, the same single rewrite pass adds them (the model sees its draft and changes only what is needed).
- **The post's programming language at your current job.** Your current job's bullets cover the posting's main requirements, one per bullet, strongest first, and at least one of them names the programming language the post asks for most, where the work used it, even if your notes never name it: the first one it asks for, a language the work is built in (such as Python or Go, even one the post only prefers) before SQL or a shell, and a requirement that offers two ("C/C++", "Python or Go") is met by either; when the post names none, the one that kind of work is usually built in (Python for AI, LLM and data work, TypeScript for web front ends, Swift for iOS, or the language or stack the job title names, such as C# for a .NET developer), unless your notes for that job name another. Work that is not built in code (nursing, sales, marketing, business development) gets no language, unless one of the post's required skills is a language on its own (SQL for a marketing analyst). Unless your hints or project notes name it, the bullet is flagged "Added to match the posting (Python). Confirm you can speak to it in an interview, or remove it." A draft whose current job misses it is fixed in the one rewrite pass, and the Format notes say so while it is still missing. The app reads a language the way people write it ("the Go payment gateway", "C++17", "Python-based"), and names that are also everyday words carefully: "Go-to-market", "R&D", "Series C", "Hepatitis C testing" or "a Class C driver's license" never count as Go, R or C, and "SQL Server" in a post is a database, not the SQL language. Resumes made before the one-page rule keep their own notes.
- **Keywords match the posting; sentences never copy it.** The required skills are keywords as people list them on a resume ("SQL", "AWS", "React"), never pieces of the posting's sentences ("advanced SQL statements", "AWS-hosted systems"); a list of examples ("AI tools like Copilot, Cursor, or Claude Code") becomes the tools themselves. Around each keyword, the summary and bullets say what you did in their own words. The app finds anything copied word for word from the job description (four or more words in a row, in any tense) and skills written as phrases; two or more copies, or any phrase skill, are fixed in the same single rewrite pass, and the Format notes point out anything left.
- **A career that builds toward the job.** Before writing, the model plans what each job will show from the job description: older jobs show the foundations of what the posting asks for, each later job adds scope (implemented, built, designed, owned, led), and the most recent job covers the posting's core responsibilities. Each job's bullets describe work on that company's main product or service during those dates, using its real public product names when the model knows the company; for a company it does not know, the business stays generic and no product names are invented.
- **Only tools that were really in common use.** A job mentions a tool only if it was common at work during that job, not merely released (for example GitHub Actions from 2020, OpenTofu from 2024). AI tools (LLMs, ChatGPT, AI coding assistants, agentic development) appear only at the one or two most recent jobs, and never before they became popular (LLMs and AI coding assistants 2023, agentic development 2025). The app checks this itself and has the model move such a tool in the one rewrite pass.
- **A career path that shows growth and never steps down.** A title is never lower than the one before it (no "Software Engineer II" followed by plain "Software Engineer"): the app corrects that itself at no cost, and any other title problem is fixed in the one rewrite pass.
- **A career path that shows growth.** The model is told how long each stay was and how much experience came before it, so a stay of 2+ years shows a step up (for example "Software Engineer II") and the same title never repeats three times in a row; the Format notes warn when it does. The titles also move into the target role's field as they get closer to today: the job before your current one is already in that field ("AI Platform Engineer" or "Senior Platform Engineer" before "Senior AI Platform Engineer"), earlier jobs a step nearer the general title ("Platform Engineer", "Backend Engineer") and the oldest ones plain titles ("Software Engineer", "Junior Software Engineer"), each fitting that job's own bullets and never above the target. When no older title is in the target's field, the one rewrite pass chooses them again; when only the job before the current one is outside it, only along with other fixes. Every title stays a suggestion, flagged "Use a title you can honestly claim." Apart from the most recent job, which always has the most, long stays also get more bullets than short ones (a 3-year role before an 8-month one).
- **ATS-friendly layout, built for a quick scan.** The headline under your name is large and is your most recent job title, word for word, so the line under your name, the summary's first words and your current job read the same ("Senior AI Platform Engineer"; a summary that opens with the role in other capitals or without its level gets the exact title from the app, at no cost); it is never the posting's full title with its team, brackets or skills ("Senior Data Engineer | Python | SQL" becomes "Senior Data Engineer"): your domain and tools are in the summary, Skills and the bullets. A special posting title is never copied: for a "Senior Voice AI Engineer" post the headline, the summary and your job titles say "Senior AI Engineer", and the voice work shows in the bullets. Each job line starts with the job title, then the company, its place and the work mode in gray, with the dates on the right; a line too long for the page keeps the title and as many of the parts after it as fit beside the dates, and moves the rest (the company, the place or the work mode) to a line under it. The title line under your name and the section headings are navy, the headings in small spaced capitals with a thin gray rule beside them, and the skills labels have a column of their own, widened to fit the longest label (when that label would take more than 40% of the line, every label goes in line with its values instead). Single column, real text in Inter (embedded, four weights), standard section headings, no tables, columns, images or icons, contact details in the body. In the PDF and the Word file the contact line's email, LinkedIn and website (GitHub or portfolio) are clickable links that look like the rest of the line, while the phone and the place stay plain text. No tool can guarantee how every ATS parses a file; this follows the common advice.
- **Bad model output is handled.** Invalid or incomplete JSON is sent back once with the error; if it still fails the next fallback model is used; failures show up in History instead of crashing.

## Privacy and security
- Your resume text and job description go **only to the model you pick**, over HTTPS, with your own API key. Check each provider's retention terms; use paid keys (free tiers may let the provider train on your data).
- Stored locally in SQLite (`data/`, file mode 600): your uploaded base resumes (the facts read from them, not the files), and each run's generated resume, cover letter, the job description it was made for (kept so a cover letter can be written later) and the job post's link (kept for History, which also copies it onto each Download row until the retention period). Runs are deleted after the retention period; uploaded resumes stay until you delete them; Settings > Delete all stored data removes everything at once.
- API keys come from environment variables or your local `.env` only and are never returned by the API or stored in the database. `.env` is excluded from git. The admin can paste a key on **Settings > API keys**: it is written to `.env` (a new `.env` is readable by its owner only), and the page shows only the provider's marker and the key's last 4 characters, such as `sk-proj-...1234`. A key changed in `.env` by hand is also used at once.
- Every page needs a login. Passwords are stored as scrypt hashes; the session cookie is HttpOnly and SameSite, and is sent only over HTTPS when the site uses HTTPS (set `COOKIE_SECURE=1` on a server). Requests from other websites that change data are refused. By default the app listens on `127.0.0.1` (your computer only).
- **Hosting it online**: see **[DEPLOY.md](DEPLOY.md)** for PythonAnywhere, step by step. On any server, put a `.env` there with `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `COOKIE_SECURE=1`, `FORCE_HTTPS=1` and your API keys, and run `uvicorn app.asgi:app` (or `app.wsgi:application` on a WSGI host). PythonAnywhere free accounts can only reach allow-listed websites (Gemini works; not every provider does).
- Uploads are limited to 5 MB, 10 PDF pages and a bounded DOCX unpack size; the browser UI inserts all text with `textContent`, and pages are served with a content security policy.

## Troubleshooting

| Problem | What to do |
|---|---|
| Window closes immediately / "Python not found" | Install Python 3.11+ (tick "Add python.exe to PATH" on Windows), then run `start.bat` again |
| Anything else that will not start | `python -m app.doctor` says what is wrong and how to fix it |
| "Port 8000 is already in use" | Another copy is running. Close it, or set another port: Windows `set PORT=8001`, macOS/Linux `PORT=8001 ./start.sh` |
| Browser did not open | Open <http://127.0.0.1:8000> yourself (or set `OPEN_BROWSER=0` to stop it trying) |
| PDF preview is blank | Use **Download resume PDF** (some browsers block inline PDFs) |
| A model says "no API key" | Paste the key on **Settings > API keys** and press **Save** (or put it in `.env`). It works at once |
| A model fails on the first call | Run **Settings > Run check**: the error names the problem (key, model name, unsupported feature). Fix the entry in `models.yaml` |
| "hit the token limit" | Raise `max_output_tokens` for that model in `models.yaml` or lower its reasoning effort (reasoning tokens count too) |
| Upload says "No readable text" | The PDF is a scan (an image). Export a text PDF or DOCX from your word processor |

## Development

```bash
pip install pytest && python -m pytest        # no network or API keys needed
```

Tests cover the schemas, validation and fixed-field integrity, both provider adapters (against mocked HTTP, a local mock server, and the real Anthropic SDK pointed at a mock Messages API), routing, fallback and cost cap, the full pipeline with the demo models, the PDF/DOCX renderers, every API endpoint and the upload hardening. The browser UI was also exercised end to end with headless Chromium.

**What is not verified:** calls to the real provider APIs (no keys were available while building), the exact model strings and prices marked unverified, writing quality for any real model, and running on Windows/macOS (built and tested on Linux; the PDF engine is pure Python and `start.bat` is plain batch, but neither has been run on those systems). Use `app.doctor`, `app.cli check` and the bake-off for those.

Known limits: scanned (image-only) PDFs are not supported (no OCR); names in scripts the bundled font lacks (for example Chinese) are missing from the PDF, but not the DOCX; the rule-based reader is rough on unusual layouts (check the warnings on the Profile list, or choose an AI reader in Settings); the page-fit logic is tuned for Letter/A4 resumes of one page (two only for very long careers); with 4 or more employers the page, not the per-job limits, decides how many bullets older jobs get, often one each, since the most recent job takes about half of them; a draft of many one-line bullets can still leave a few empty lines at the bottom of the page. With the Certifications section on (Settings), the AI picks certifications for each job, but only the ones you have (from your uploaded resume, or ticked on the Tailor page) are printed: it has no way to know which ones you hold.
